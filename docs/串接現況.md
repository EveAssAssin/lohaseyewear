## 一、系統與職責

| 系統 | 負責 | 對外位址 |
|---|---|---|
| 官網 | 刻圖市集、客製文創、禮物中心、會員中心 | `www.lohasglasses.com` |
| 官網後端 | Supabase Edge Functions | `hqdmyxxrskvllkcedybl.supabase.co/functions/v1/*` |
| 商城 | 商品、購物車、訂單、金流、出貨 | `www.lohaseyewear.com` |

官網以呼叫時的金鑰標籤標記來源,測試資料事後可篩出清除。

## 二、目前各支函式對接的環境

| 官網函式 | 對接 | 環境 |
|---|---|---|
| `shop` | 商城 `/api/site/*` | **測試站** |
| `coupon-list` | 主後端 `/siteapi/coupon/*` | **正式站** |
| `member-auth` | 主後端 `/siteapi/member/*` | **測試站** |
| `shop-webhook` | 接收商城的事件 | — |
| `store-sso-login` | 供商城/App 呼叫 | — |

> 主後端的測試站與正式站使用**不同的金鑰**;商城的金鑰又與主後端不同。
> 切換環境時網址與金鑰必須一起換。

## 三、已完成並驗證的介面

### 3-1 商品查詢 `POST /api/site/{categories,products,product}`

官網以 `shop` 函式代理,金鑰不落前端。`can_design_only: 1` 取得可客製商品清單。

### 3-2 送進購物車 `POST /api/site/cart/push`

官網送出的 `main.design` 內容:

| 欄位 | 說明 |
|---|---|
| `submission_id` | **這一次送出**的唯一識別碼,由官網產生 |
| `design_id` | 刻圖作品編號(同一張刻圖可被多次送出,無法唯一對應訂單) |
| `design_name` | 刻圖名稱 |
| `engraving_url` | 雕刻檔 SVG,供加工端下載 |
| `preview_url` | 合成圖,給客人看 |
| `guide_url` | 加工位置指示圖 |
| `placement` | `{lens, scale, x, y, basis}`,座標相對於商品圖 |

- `sid` 只在商品真的有規格時才帶(無規格商品帶了會被擋)
- 不帶任何金額欄位
- `plus_buy` 帶 `engraving_fee`;商城目前不另外收費,回應以 `plus_buy_note` 說明

**已驗證**:2026-08-17 於測試站完成一筆訂單 `20260817S1ZJc0gdF0Hf`,
三張圖於商城後台皆可取得,訂單明細的「查看我的設計」可正確開啟合成圖,
刻圖位置與客人設定一致。

### 3-3 一次性登入 `store-sso-login`

商城/App 送 `apiKey` + `erpId`(+ 選填 `erpName`、`next`),換到 30 秒有效的 `reUrl`。

- 金鑰分三把:`app` / `shop` / `shop-test`,可分別輪替與停用
- `next` 只接受站內相對路徑(擋 open redirect)
- 呼叫紀錄寫入 `sso_login_log`,含金鑰標籤、`erpId`、IP、結果
- 速率限制:每把金鑰每分鐘 60 次;短時間內大量不同 `erpId` 會告警但不擋

> 該金鑰等同於「可為任意會員產生登入連結,不需要那位會員的密碼」,
> 雙方均以高於一般 API 金鑰的等級保管,不經通訊軟體傳遞。

## 四、已完成但尚未接通的介面

### 4-1 官網的 Webhook 接收端

```
POST https://hqdmyxxrskvllkcedybl.supabase.co/functions/v1/shop-webhook
Header: X-Lohas-Webhook-Key
```

| `event` | 必要欄位 | 官網行為 |
|---|---|---|
| `gift_paid` | `event_id`, `gift_id`, `order_no` | 禮物 → `paid` |
| `gift_shipped` | `event_id`, `gift_id` | → `shipped` |
| `gift_redeemed` | `event_id`, `gift_id` | → `redeemed` |
| `gift_cancelled` | `event_id`, `gift_id` | → `cancelled` |
| `design_order` | `event_id`, `order_no`, `submission_id`, `design_id`, `nid`, `client_id` | 回填訂單編號 |

回應約定:`200` 已受理或已處理過(不需重試)、`401` 金鑰不符、`500` 暫時性錯誤(請重試)。
以 `event_id` 冪等。資料對不上時回 `200` 而非 `500` —— 那種情況重試不會變好,
事件已留底供事後處理。禮物狀態採條件更新,不需要保證事件順序。

**`design_order` 對所有含 `main.design` 的訂單發送**,不限禮物訂單 ——
門市查刻圖要查的多數是一般客製單。

## 六、待確認

### 6-1 測試站的 `healthz/smscode` 未反映新產生的驗證碼

官網以 `verify_type=sms` 在測試站送出註冊,`register_send` 回 `200`,
但該端點的 `signup` 為空陣列,`login` 組唯一一筆為十天前產生、`seconds_left` 為 0,
加上快取避開參數後結果相同。**待確認取碼方式。**

在此之前官網的註冊入口維持關閉 —— `member-auth` 指向測試站,
若開放,使用者的帳號會建在測試環境而無法登入。

### 6-2 商城後台新增商品時無欄位層級的錯誤訊息

於測試站後台新增眼鏡商品,必填欄位皆已填寫,送出後顯示「新增失敗」,
頁面與回應均無指出是哪一欄。**待確認原因。**

### 6-3 合成圖在購物車的呈現

商城購物車與訂單明細的商品圖由 360 度旋轉檢視器渲染,
官網送出的 `preview_url` 以「查看我的設計」連結呈現(商城已完成)。

## 七、已達成的約定

| 主題 | 結論 |
|---|---|
| 禮物逾期 | 自付款起 90 天未領取即作廢,後台可人工退,不做自動退款 |
| 門市兌換換規格 | 不開放。`placement` 座標綁定商品圖,換款後座標失去意義 |
| 收禮人非會員 | 領取連結誰都能開,**領取時才需登入** |
| 一份禮物多件商品 | 第一階段單件 |
| 發券失敗 | **不退回可領取狀態**。`claimed`(歸屬)與 `issued`(發券)是兩個狀態,歸屬已定不可逆 —— 退回會讓禮物在重試期間被持有連結的其他人領走 |
| `gift/issue` 錯誤碼 | 分三類:可重試 / 不可重試 / 已發過。已發過須一併回傳既有的 `coupon_id` |
| 兌換券有效期 | `expires_at` 選填,不帶即無期限。官網一開始不帶 |
| 刻圖費 | 已含在商品售價內,不另外收費 |
| B 路線的履約 | 第一階段只做門市自取。宅配與超取需要一支「訂單成立後補上設計」的介面,暫不開發 |

## 八、名詞

| 詞 | 意義 |
|---|---|
| A 路線 | 送禮人挑好鏡框與刻圖後付款,收禮人領取即完成 |
| B 路線 | 送禮人購買通用禮物商品,收禮人領取後自己挑鏡框與刻圖 |
| `submission_id` | 官網每一次 `cart/push` 產生的唯一識別碼,亦為官網送單紀錄的主鍵 |
| `erpId` / `client_id` | ERP 客戶編號。官網註冊的會員此欄為空,需到門市綁定 |
| `mid` | App 會員編號。尚未綁定 ERP 的會員以此識別 |
