## 三、已完成並驗證的介面

### 3-1 商品查詢 `POST /api/site/{categories,products,product}`

官網以 `shop` 函式代理,金鑰不落前端。`can_design_only: 1` 取得可客製商品清單。

### 3-2 送進購物車 `POST /api/site/cart/push`

官網送出的 `main.design` 內容:

> ⚠ **「白」欄的意思:這個鍵有沒有在【官網 `shop` 函式】的白名單裡。**
> 沒有打勾的欄位,官網送出去時就會被自己的白名單丟掉 ——
> 回應仍然是 200,值卻不見了,**兩邊都看不出異常**。
>
> `placement`(2026-08)與 `claim_url`(2026-08-28)兩次都是同一個形狀:
> 改白名單的人手上只有「要擋什麼」,沒有「講好要收什麼」,
> 而那份清單只存在於信件往來裡。所以從現在起寫在這張表上。
>
> 商城端也有自己的白名單,**兩邊各有一份,要各自確認**。

#### 3-2-1 `main.design`(只在真的有刻圖時才帶)

| 欄位 | 白 | 說明 |
|---|:--:|---|
| `submission_id` | ✅ | **這一次送出**的唯一識別碼,由官網產生 |
| `design_id` | ✅ | 刻圖作品編號(同一張刻圖可被多次送出,無法唯一對應訂單) |
| `design_name` | ✅ | 刻圖名稱 |
| `engraving_url` | ✅ | 雕刻檔 SVG,供加工端下載。**未通過網址檢查就整個不帶** |
| `preview_url` | ✅ | 合成圖,給客人看。同上 |
| `guide_url` | ✅ | 加工位置指示圖。同上 |
| `placement` | ✅ | `{lens, scale, x, y, basis}`,座標相對於商品圖 |

#### 3-2-2 `gift`(只在送禮時才帶)

| 欄位 | 白 | 說明 |
|---|:--:|---|
| `is_gift` | ✅ | 固定 `true` |
| `gift_id` | ✅ | 我方 `gifts` 那一列的主鍵,付款完成時以它回拋 `gift_paid` |
| `fulfillment` | ✅ | `store` / `ship`。**2026-08-27 起一律 `store`**(宅配已關閉) |
| `recipient_erpid` | ✅ | 選填,有值才帶 |
| `claim_url` | ✅ | 2026-08-28 新增。給商城訂購完成頁放「複製連結 / LINE 分享」。<br>**只放行 `https://www.lohasglasses.com/` 開頭**,其餘丟棄 |

> `claim_url` 提早交出去領不了:`claim` 硬性要求 `status === 'paid'`,
> `pending_payment` 明確擋掉。它只是「先放在對方頁面上」,不是提前開放領取。

- `sid` 只在商品真的有規格時才帶(無規格商品帶了會被擋)
- 不帶任何金額欄位
- `plus_buy` 帶 `engraving_fee`;商城目前不另外收費,回應以 `plus_buy_note` 說明
- `placement` 與 `submission_id` 由商城**原樣保存、不解析**,上限 4KB;
  超過則整包不收並記錄(截斷過的 JSON 看起來有值卻解不開,比沒有更糟)

**已驗證**:2026-08-17 於測試站完成一筆訂單 `20260817S1ZJc0gdF0Hf`,
三張圖於商城後台皆可取得,訂單明細的「查看我的設計」可正確開啟合成圖,
刻圖位置與客人設定一致。

> 該筆成立於 `placement` 修正之前,`placement` 的保存待新的測試單確認。

### 3-3 一次性登入 `store-sso-login`

商城/App 送 `apiKey` + `erpId`(+ 選填 `erpName`、`next`),換到 30 秒有效的 `reUrl`。

- 金鑰分三把:`app` / `shop` / `shop-test`,可分別輪替與停用
- `next` 只接受站內相對路徑(擋 open redirect)
- 呼叫紀錄留底,含金鑰標籤、`erpId`、IP、結果
- 速率限制:每把金鑰每分鐘 60 次;短時間內大量不同 `erpId` 會告警但不擋

> 該金鑰等同於「可為任意會員產生登入連結,不需要那位會員的密碼」,
> 雙方均以高於一般 API 金鑰的等級保管,不經通訊軟體傳遞。

### 3-4 票券 `POST /siteapi/coupon/list`

官網以 `coupon-list` 函式代理,已指向主後端**正式站**。

2026-08-19 以真實會員登入驗證:回 `code 200`,共 19 張(可用 6、已過期 13),
與該會員在樂活 App 票券頁看到的內容一致。

> 官網目前**不顯示票券清單** —— 票券由 App 負責顯示與使用。
> 這支函式保留是給「App 點票券跳進官網客製頁」的流程用的
> (取得可換分類、定期續鎖)。

### 3-5 會員 `POST /siteapi/member/*`

官網以 `member-auth` 函式代理,已指向主後端**正式站**並驗證通過。

- 官網補上 `client_ip`(取自 `x-forwarded-for`)
- 兩段速率限制:寄送類 10 次/小時、查詢類 30 次/分鐘
- 呼叫紀錄只記 action 與回應代碼,**不記內容**(內含密碼與驗證碼)

## 四、已完成但尚未接通的介面

### 4-1 官網的 Webhook 接收端

```
POST https://hqdmyxxrskvllkcedybl.supabase.co/functions/v1/shop-webhook
Header: X-Lohas-Webhook-Key
```

| `event` | 必要欄位 | 官網行為 |
|---|---|---|
| `gift_paid` | `event_id`, `gift_id`, `order_no` | 禮物 → `paid` |
| `gift_shipped` | `event_id`, `gift_id` | → `shipped` |
| `gift_redeemed` | `event_id`, `gift_id` | → `redeemed` |
| `gift_cancelled` | `event_id`, `gift_id` | → `cancelled` |
| `design_order` | `event_id`, `order_no`, `submission_id`, `design_id`, `nid`, `client_id` | 回填訂單編號 |

回應約定:`200` 已受理或已處理過(不需重試)、`401` 金鑰不符、`500` 暫時性錯誤(請重試)。
以 `event_id` 冪等。資料對不上時回 `200` 而非 `500` —— 那種情況重試不會變好,
事件已留底供事後處理。禮物狀態採條件更新,不需要保證事件順序。

**`design_order` 對所有含 `main.design` 的訂單發送**,不限禮物訂單 ——
門市查刻圖要查的多數是一般客製單。

### 4-2 發券 `gift/issue`

回應格式:

```json
{ "code": "OK", "coupon_id": 123456, "retryable": false }
```

| `code` | 類別 | 官網的處理 |
|---|---|---|
| `OK` | 成功 | 推進到 `issued` |
| `ALREADY_ISSUED` | 已發過 | 視為成功,寫入回傳的 `coupon_id` |
| `TEMPORARY` | 可重試 | 退避重試 |
| `INVALID_PARAM` / `ITEM_NOT_FOUND` / `MEMBER_NOT_FOUND` | 不可重試 | 停止並通知 |

**未知的 `code` 一律以 `retryable` 布林值為準** —— 日後新增代碼時官網端不需改程式。

`ALREADY_ISSUED` 必須一併回傳既有的 `coupon_id`:只回「重複」的話,
官網會停在 `claimed` 拿不到券號,收禮人的票券頁看得到券、禮物中心卻永遠顯示「準備中」。

## 七、已達成的約定

| 主題 | 結論 |
|---|---|
| 禮物逾期 | 自付款起 90 天未領取即作廢,後台可人工退,不做自動退款 |
| 門市兌換換規格 | 不開放。`placement` 座標綁定商品圖,換款後座標失去意義 |
| 收禮人非會員 | 領取連結誰都能開,**領取時才需登入** |
| 一份禮物多件商品 | 第一階段單件 |
| 發券失敗 | **不退回可領取狀態**。`claimed`(歸屬)與 `issued`(發券)是兩個狀態,歸屬已定不可逆 —— 退回會讓禮物在重試期間被持有連結的其他人領走 |
| `gift/issue` 錯誤碼 | 見 4-2 |
| 兌換券有效期 | `expires_at` 選填,不帶即無期限。官網一開始不帶 |
| 刻圖費 | 已含在商品售價內,不另外收費 |
| B 路線的履約 | 第一階段只做門市自取。宅配與超取需要一支「訂單成立後補上設計」的介面,暫不開發 |
| 金鑰的環境對應 | 商城與主後端各用各的環境變數,不共用、不設互相備援 |

## 九、未綁定門市會員(`client_id` 為空)可以做什麼

官網於 2026-08-19 開放註冊,這種會員自此會實際存在。兩邊的處理已對齊:

| 功能 | 未綁定會員 | 說明 |
|---|---|---|
| 登入官網、瀏覽刻圖與商品 | ✅ | |
| **領取禮物(A、B 兩條路線)** | ✅ | 官網記在 `claimed_by_mid`,發券以 `mid` 呼叫 `gift/issue` |
| 在禮物中心看自己領了什麼 | ✅ | |
| 自己挑鏡框與刻圖(B 路線) | ❌ | 要送 `cart/push`,商城需要 `client_id`。介面改為指路到門市 |
| 票券(`coupon/list`、`lock`) | ❌ | 票券 API 以 `client_id` 為索引 |
| 客製下單、送禮、收藏 | ❌ | |

**綁定後的回填**:主後端把 `owner_mid` 搬到 `client_id` 並清空;
官網把 `claimed_by_mid` 搬到 `claimed_by_erpid` 並清空。
兩邊都是「搬過去並清空」而非兩欄並存 —— 並存的話,該會員日後解除綁定,
兩個身分會各自從不同欄位看到同一筆資料。

> ⚠ 官網端的回填由**本人下一次帶著登入狀態進站**時觸發。
> 門市剛完成綁定的當下資料還沒搬,以會員編號查刻圖會查不到 ——
> 請客人在手機上開一次官網會員專區即可。
