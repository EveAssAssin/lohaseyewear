# 禮物中心 — 商城端需求規格

> 樂活眼鏡官網．2026-08-09．v0.2（提案，待貴方確認）
> 對應官網功能：會員 A 買一份「刻圖 ＋ 眼鏡」送給會員 B。

---

## 一、要做什麼

官網的刻圖市集新增「送禮」流程。A 選好刻圖、眼鏡、規格之後，可以選兩種履約方式：

| 方式 | 說明 | 收件地址 |
|---|---|---|
| **宅配到府** | A 在商城結帳時直接填收件地址（可以填 B 家） | A 在商城填，官網不經手 |
| **門市兌換** | 付款後發一張兌換券到 B 的帳號，B 到門市出示、現場配鏡雷刻 | 沒有地址 |

**兩條路的前半段完全相同**，都是官網把「商品 ＋ 刻圖 ＋ 刻圖位置」推進購物車，
由 A 在商城完成付款。差別只在付款之後。

**設計上刻意避開的事**：官網不儲存任何收件地址。
宅配的地址在貴方系統、門市兌換沒有地址，官網只保管刻圖與禮物關係。

## 二、需求一：訂單要帶「刻圖位置」（兩條路都需要）

**現況**：`cart/push` 草案的 `design` 區塊有 `preview_url` 與 `engraving_url`，
但**沒有位置資訊**。雷刻人員不知道要刻在鏡片的哪裡、多大。

**需求**：`design` 增加 `placement`，並新增 `gift` 區塊。

```json
{
  "client_id": "28095839",
  "main": {
    "nid": 1234,
    "sid": 18,
    "amount": 1,
    "design": {
      "design_id": "官網端的設計編號",
      "preview_url": "https://....supabase.co/.../preview.png",
      "engraving_url": "https://....supabase.co/.../engraving.svg",
      "placement": {
        "lens": "right",
        "size": 0.38,
        "dx": -0.24,
        "dy": -0.08
      }
    }
  },
  "plus_buy": [ { "type": "engraving_fee", "amount": 1 } ],

  "gift": {
    "is_gift": true,
    "gift_id": "官網的禮物編號（uuid）",
    "fulfillment": "store",
    "recipient_erpid": "28095198"
  }
}
```

**`placement` 的單位說明**：以**雙眼間距**為基準的倍率，不是像素。
`size:0.38` ＝ 刻圖寬度為雙眼間距的 38%；`dx/dy` 為相對眼睛中心的偏移，負值代表往外側／往上。
這樣定義的好處是與鏡框尺寸、照片解析度都無關，換任何鏡框都能換算。

若貴方系統不方便解析這組參數，替代方案：**只傳 `design_id`**，
雷刻人員到官網後台查該筆設計的位置圖（官網會另做一個門市查詢頁）。
這個方案對貴方改動最小，我方也可接受。

| `gift` 欄位 | 說明 |
|---|---|
| `is_gift` | 這筆是禮物 |
| `gift_id` | 官網禮物編號，後續回拋都靠它對應 |
| `fulfillment` | `ship` 宅配／`store` 門市兌換 |
| `recipient_erpid` | 收禮會員（`store` 必填；`ship` 可空） |

## 三、需求二：付款完成要回拋通知官網（兩條路都需要）

**現況**：官網不知道 A 付了沒。沒付款就讓禮物成立，等於白送。

**需求**：訂單**付款完成**時，商城打一支 webhook 到官網。

```
POST https://hqdmyxxrskvllkcedybl.supabase.co/functions/v1/gift-webhook
Header: X-Shop-Key: （由官網提供給貴方的金鑰，與票券金鑰不同把）
```

```json
{
  "event": "gift_paid",
  "gift_id": "官網的禮物編號",
  "order_trade_no": "商城訂單編號",
  "paid_at": 1754584200
}
```

**官網回應**：`{ "code": "200" }`

- 非 `200` 請重試，建議 3 次（間隔 1 / 5 / 30 分鐘）
- 同一 `gift_id` 重複送不會出錯，官網以 `order_trade_no` 做冪等處理
- 請用**付款完成**而非建立訂單。與票券 `redeem` 相反：
  票券怕鎖定逾時所以要早，禮物則是付款前不能讓人領走

**另請一併回拋這些事件**：

| event | 時機 | 適用 | 額外欄位 |
|---|---|---|---|
| `gift_paid` | 付款完成 | 兩者 | `order_trade_no` |
| `gift_shipped` | 實際出貨 | 宅配 | 物流單號（若有） |
| `gift_redeemed` | 門市核銷完成 | 門市 | `coupon_id`、`store` |
| `gift_cancelled` | 訂單取消／退款 | 兩者 | 原因 |

## 四、需求三：門市兌換要發券給第三方（僅門市路徑）

**這是唯一一項真的需要新開發的功能。**

請提供一支發券介面，由**官網在確定收禮人之後**呼叫：

```
POST /api/site/gift/issue
```

```json
{
  "gift_id": "官網的禮物編號",
  "order_trade_no": "商城訂單編號",
  "recipient_erpid": "28095198",
  "design_id": "官網端的設計編號"
}
```

**回應**

```json
{ "code": "200", "data": { "coupon_id": 123456 } }
```

**為什麼不是付款完成時自動發券**：送禮者用「連結」方式送出時，
付款當下收禮人還不存在——要等對方點連結、登入，官網才知道要發給誰。
改由官網主動呼叫，指定會員與連結兩種模式就能用同一條路，
貴方也不必判斷該不該等。

同一 `gift_id` 重複呼叫請回傳既有的 `coupon_id` 而非重複發券。

券的內容需綁定這份禮物的商品與刻圖。
建議發券時把 `gift_id` 一併存進票券，門市核銷時就能反查刻圖檔與位置圖。

**為什麼建議走票券系統而不是另開一套**：貴方票券已經有
App 內顯示、門市掃碼 QRCode、狀態機、鎖定防重複核銷。
禮物走同一套的話，App 端可能連新畫面都不用做。

票券文件第十節寫「須轉贈他人使用的票券一律不開放官網使用」——
理解上那是指**不開放官網折抵**，不影響門市核銷，這裡走的正是門市那條。
若理解有誤請告知。

**若貴方認為不該用票券系統**，也可以是任何形式的兌換憑證，
只要滿足：① 掛在收禮人帳號下 ② 門市能核銷 ③ 能帶到刻圖資訊。

## 五、需要貴方確認的問題

1. **`placement` 貴方要解析，還是走 `design_id` 讓門市到官網後台查？**
   後者對貴方改動最小，我方傾向這個。

2. **發券給第三方會員**，貴方系統目前做得到嗎？需要多少工期？

3. **門市兌換的規格彈性**：A 選了霧黑 54mm，B 到店想換玳瑁色。
   券是綁死商品規格，還是綁「可兌換分類」讓店員現場處理？
   我方傾向後者——這正是門市兌換相對宅配最大的優勢。

4. **收禮人一直不領怎麼辦？** 官網預計設 90 天失效。
   屆時要走退款嗎？全額退給 A、還是轉成 A 帳上的購物金？

5. **webhook 金鑰**：官網會另發一把給貴方（與票券的 `X-Site-Key` 不同把），
   避免任一把外洩時波及另一邊。請確認貴方能設定自訂 Header。

6. **測試環境**：`lohas-shop-test.onrender.com` 上能否先開這幾支？
   官網端會先做到「待付款」狀態，接上後就能全鏈路測試。

## 六、與 v0.1 的差異（若貴方已看過前一版）

前一版假設「B 領取時才填地址」，因此要求貴方提供
`hold_shipping`（暫緩出貨）與 `order/recipient`（補收件資訊）。

**這兩項已取消。** 改為宅配路徑由 A 在商城結帳時直接填地址，
走貴方原有的一般訂單流程，不需要任何暫停或補件機制。
