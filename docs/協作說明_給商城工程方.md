## 二、⚠ 三件絕對不能做的事

### 2-1 不要把任何金鑰寫進程式碼

`docs/edge-functions/` 底下每一支都有 `FALLBACK_*` 常數,而且**永遠是空字串**:

```ts
const FALLBACK_SITE_KEY = '';        // ← 保持這樣
```

真正的值只填在 Supabase Dashboard 的線上版本,由樂活這邊手動貼上。
你在 repo 裡看到空字串**不是遺漏,是刻意的** —— 這個 repo 全世界都看得到。

若你的修改需要新的金鑰,請在程式碼裡留空常數並在 PR 說明中註明,由樂活填值。

### 2-2 不要動這兩個開關

| 位置 | 現況 | 為什麼 |
|---|---|---|
| `js/register.js` 的 `NOT_READY = true` | 註冊入口關閉 | `member-auth` 目前指向主後端**測試站**。開放的話,使用者的帳號會建在測試環境然後登不進來 |
| `docs/edge-functions/shop.ts` 的 `SHOP_BASE` | 指向商城**測試站** | 貴方明確要求「正式站部署完成前維持在測試站驗證」 |

看起來像「忘了改回來」的東西,多半是刻意的。動之前先問。

### 2-3 不要假設有測試環境

**官網與 Supabase 只有一套環境,沒有測試站。**
你在商城測試站做的每一次操作,都會寫進官網的正式資料表
(`design_submissions`、`gifts`、`sso_login_log`)。

因此:**在商城測試站測試時,只用內部人員的 ERP 客編。**
`erpId` 是全公司共用的編號,拿其他客編呼叫 `store-sso-login`,
換到的會是**那位真實客人**的官網登入連結。

## 三、你能改什麼、怎麼交付

### 可以直接改

| 範圍 | 檔案 |
|---|---|
| 前端頁面與樣式 | 根目錄 `*.html`、`css/`、`js/` |
| Edge Function 邏輯 | `docs/edge-functions/*.ts` |
| 資料表結構 | `docs/*.sql`(只寫 SQL,不要嘗試連線執行) |

### 交付方式:fork + Pull Request

**請不要直接 push 到 main。** 兩邊各自 commit 會互相覆蓋,而且審查責任會不清楚。

```bash
# 你的 fork
git checkout -b fix/描述性的名字
# 改動
git commit
# 發 PR 到 EveAssAssin/lohaseyewear
```

PR 內容請說明:改了什麼、為什麼、以及**是否需要重新部署 Edge Function**。

### 部署由樂活這邊做

Edge Function 不是自動部署的 —— 樂活的人會把檔案貼進 Supabase Dashboard。
所以你的 PR 合併之後**不會立刻生效**,需要樂活手動部署那一步。
若你的改動需要部署,請在 PR 裡明確寫出來。

## 四、寫程式的慣例

這個專案有一致的風格,請沿用:

| 項目 | 慣例 |
|---|---|
| 語言 | 註解、commit、文件一律**繁體中文** |
| 註解 | 寫**為什麼**這樣做,不寫程式碼在做什麼。尤其是「看起來多餘但不能刪」的東西 |
| JS | 前端用 ES5 風格的 `var` / `function`(不經編譯直接上線,要顧舊瀏覽器);Edge Function 用現代 TypeScript |
| CSS | 顏色一律取 `css/lohas-tokens.css` 的變數,不寫死色碼 |
| 快取 | 改了 `js/*.js` 或 `css/*.css`,要同步更新引用它的 HTML 裡的 `?v=` 版號,否則使用者拿到舊檔 |

### 關於註解

這個專案的註解密度偏高,而且刻意如此。例如:

```ts
// k.key && 這個條件不能省:沒填的常數是空字串,少了它,
// 對方送一個空的 apiKey 就會比對成功。
const caller = API_KEYS.find((k) => k.key && k.key === apiKey);
```

若你發現某段程式看起來可以簡化,**先看有沒有註解解釋為什麼不行**。
沒有註解又想不通的,在 PR 裡問,不要直接改。

## 五、檔案地圖

```
docs/串接現況.md          ← 先讀這個。雙方的介面契約與目前狀態
docs/edge-functions/      ← 伺服器端邏輯,線上跑的就是這些
  shop.ts                 商城 API 代理(商品、cart/push)
  shop-webhook.ts         接收商城事件
  gift.ts                 禮物中心
  auth-session.ts         登入與 session token
  member-auth.ts          會員註冊、忘記帳密
  coupon-list.ts          票券
  store-sso-login.ts      一次性登入連結(供貴方呼叫)
  img-proxy.ts            商品圖的 CORS 代理
docs/*.sql                資料表結構
CLAUDE.md                 樂活這邊的工作準則,可一併參考
js/design.js              客製文創(合成圖、加工位置圖、送購物車)
js/gift-*.js              禮物中心與領取頁
```

**要理解串接的實際行為,讀 `docs/edge-functions/shop.ts` 的 `buildCartBody()`**——
那是官網送給 `cart/push` 的內容的唯一真相,比任何規格文件準確。

## 六、有疑問時

- **介面規格的疑問** → 先看 `docs/串接現況.md`,那裡有雙方談定的結論
- **為什麼這樣寫** → 先看程式碼註解
- **仍不確定** → 在 PR 裡提出,或透過既有的窗口詢問。**不要用猜的改**

特別提醒:這個系統有幾處「看起來是 bug、其實是刻意」的地方
(空金鑰、關閉的入口、指向測試站的設定)。改之前確認一下,比改完再回退省事。
